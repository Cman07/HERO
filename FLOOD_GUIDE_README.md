# HERO — Historical Virginia-build notes

This file records the earlier Virginia intake and feature stages. For the current nationwide ZIP survey, map, profile fields, API contracts, and verification steps, use [README.md](README.md). The Azure and account setup notes below are retained as implementation history; follow the current `.env.example` and README when running HERO.

The local F2 page keeps its three-question intake. F3 uses the selected need to order and explain referrals to DisasterAssistance.gov and FEMA's Disaster Recovery Center locator. These referrals work without the AI service and do not claim that assistance or a center is currently available. The page also opens an AI chat after the final answer. Chat sends the answers and conversation to an Azure OpenAI deployment through `server.mjs`, which keeps the API key off the browser.

The locality question uses a searchable list of Virginia's 95 counties and 38 independent cities from the [U.S. Census Bureau county geography list](https://tigerweb.geo.census.gov/tigerwebmain/Files/acs25/tigerweb_acs25_county_2024_acs24_va.html). The list is bundled locally, so filtering works even when the page is opened without the chat server. Selecting a locality confirms the choice; no free-text locality is sent to the chat.

## Household profile (Plan ahead)

`plan.html` provides a centered, four-step optional form for home locality, household size, pregnancy, children, older-adult support, disability/access needs, mobility, medical-device electricity, transportation, and pets/service animals. Every personal question supports “Prefer not to say.” Residents can review, update, and delete their profile.

Profiles are persisted in a local SQLite database under `.data/profiles.sqlite`. The payload is encrypted with AES-256-GCM; the random 32-byte encryption key is stored separately in `.data/profile.key`. Both are excluded from Git and the static server allowlist. Keep the database and key private; back them up together. Encryption does not protect against someone with access to both files or the running server.

## F5: optional local accounts

The [original feature chart](https://chatgpt.com/share/6ab5afbc-f3f8-83ea-ae7b-46b3a61557b2) defines F5 as optional sign-in and private save/edit/delete controls. Open **Sign in** from the header or **Manage account** on Plan ahead. Create an account with a username (3–32 characters) and password (12–128 characters). Account credentials are local to this running HERO site; Google sign-in and explicit linking are supported when configured; password recovery is not available.

Accounts and hashed session tokens persist in `.data/accounts.sqlite`. Passwords use Node's asynchronous scrypt with a random salt; plaintext passwords are never stored. Account sessions use random HttpOnly, SameSite=Strict cookies, expire after 30 minutes of inactivity or 7 days total, and are revoked on sign-out. Production cookies add Secure; serve over HTTPS for public use. Login/register attempts are limited to 10 per address per 15 minutes within the running server process. Keep `.data` private and back it up with the profile encryption key.

While signed in, the server loads and modifies only that account's profile. A resident can sign in from a new browser connected to the same running site and retrieve the same record. The profile owner is determined by the server session, never by a submitted account or profile ID. Deleting a household profile keeps the account and sign-in intact. The form asks for confirmation before deleting and detects account changes before saving or deleting.

Guests can still use Find help now immediately and save an optional browser-only profile as before. An opaque `hero_profile` cookie associates that browser with its encrypted record. A browser-only profile does not sync between devices; anyone using that browser can see it. Signing in never silently imports it or overwrites an account profile. The account page offers an explicit consent step to move the browser profile into an empty account; a successful move removes the browser-only copy. Sign out after using an account on a shared browser.

**Saved health, disability, access, and support answers never enter the AI request.** The “Find help now” flow shows private household reminders alongside official referrals. An unchecked-by-default option lets the resident share only saved home locality and household size with Azure AI alongside the fresh questionnaire. The server retrieves those two fields from that browser's database record; client-supplied profile IDs or extra profile fields are ignored. Home locality is never automatically assumed to be current or damage locality. Chat messages are still transmitted to Azure, so the UI asks residents not to type private health or identifying details.

The older home-only localStorage profile is not automatically migrated. Create a household profile on the new page. Immediate-danger answers continue to direct residents to 911 without calling AI.

## Run locally

1. Use Node.js 24.14 or later (the database uses built-in `node:sqlite`). Copy `.env.example` to `.env`.
2. For a hosted Microsoft Foundry agent, set `FOUNDRY_AGENT_ENDPOINT` to its Responses endpoint. Install Azure CLI, run `az login`, and grant the signed-in account the Foundry Agent Consumer role (or a higher Foundry role) on the project or agent. The server gets short-lived Entra tokens from Azure CLI and keeps them in memory; it does not use an API key for the agent endpoint. When this setting is present, it takes priority over the direct model settings.
3. Alternatively, for a direct chat-model deployment, fill in the endpoint, deployment name, and API key from your Azure AI Foundry resource. Keep `.env` private.
4. Run `npm start`. The server loads `.env` if present and creates the local profile database. Restart the server after changing server routes or configuration.
5. Open `http://127.0.0.1:3000`.

For a direct model deployment, the endpoint should be the resource origin, for example `https://YOUR-RESOURCE.openai.azure.com` or `https://YOUR-RESOURCE.services.ai.azure.com`. The server calls the Azure OpenAI v1 chat completions route and uses the deployment name as `model`. For a hosted agent, the server calls the configured Responses endpoint, which uses the agent's Foundry instructions. Without either configuration, the page and questionnaire still work, but the chat reports that it is unavailable.

The assistant uses only the two supplied federal destinations for referrals and is instructed not to claim current conditions, application status, center availability, or eligibility. Those instructions reduce risk but cannot guarantee every model answer. Review the emergency wording and model behavior before public use. This local project does not contain the prior Sites source or its hosting configuration, so these changes are not published to that Site.

Run `npm test` to check encrypted profile persistence, browser/account isolation, password hashing, session expiry and sign-out, profile validation and CRUD, exclusion of sensitive fields from AI requests, the emergency gate, and static page routes. Tests use temporary databases and a mocked Azure response. Real chatbot replies require your Azure configuration.


## Google sign-in and linking

The account page offers Google sign-in alongside the existing username/password form. If `GOOGLE_CLIENT_ID` is empty, it displays an unavailable message and continues to support local accounts and guests. Profiles stay in the encrypted local SQLite database. Google receives the sign-in interaction, not the household questionnaire. No Gmail or Drive access is requested.

1. In [Google Cloud](https://console.cloud.google.com/), create/select a project. Configure Google Auth Platform branding, audience and test users if using testing mode. Create a **Web application** OAuth client.
2. Register **Authorized JavaScript origins** for `http://localhost:3000` and, once private access is ready, the exact HTTPS address printed by `npm run start:private`. This implementation uses the Google Identity Services popup/callback flow; it does not need a client secret or an authorized redirect URI.
3. Put the client ID ending in `.apps.googleusercontent.com` into `GOOGLE_CLIENT_ID` in the existing `.env` file. Keep existing Azure settings. Restart HERO.
4. Open the registered origin's `/account.html`. Google-only sign-in creates an account with an internal generated username. Return with the same Google account on another connected device to load the same profile.
5. To preserve an existing username/password profile, **sign in with that username first**, then use **Link your Google account**. After linking, either method opens that same account. Signing in with Google while signed out creates/opens its own account; matching emails never silently merge profiles. If Google already belongs to another HERO account, linking is refused; existing profiles are kept.

The server uses Google's official `google-auth-library` to check signatures, audience, issuer and expiry, then checks the nonce and verified email. A ten-minute, one-use SQLite challenge binds sign-in/linking to the browser and the original account session. Google identities are keyed by Google's stable `sub`, not email. The account database migrates existing password accounts in place without changing their profile owner, password hash or sessions. ID tokens are not persisted or logged.

## Private access from other devices (SQLite stays on this computer)

1. Install the official app with `brew install --cask tailscale`. The macOS installer requires your administrator password. Open Tailscale, sign in and approve the macOS VPN setup yourself.
2. Install/sign in to Tailscale on each phone or computer that needs access, using your private network. Restrict access to your own devices.
3. Stop the existing `npm start` process so port 3000 is available. In this HERO directory, run `npm install`, then `npm run start:private`.
4. The helper discovers the connected computer's Tailscale DNS name, starts HERO on loopback, enables Secure cookies and checks writes against that exact HTTPS origin. It runs `tailscale serve --bg http://127.0.0.1:3000` and prints your private HTTPS account-page URL. Follow Tailscale's HTTPS activation instructions if prompted, then retry. It uses **Serve**, which is private to your network.
5. Register that HTTPS origin in Google Cloud as above. On another connected device, open the same HTTPS URL and sign in. Existing profiles remain on this computer; it must stay awake, online, and running HERO.

Ctrl+C stops HERO. The Serve proxy may remain configured; `tailscale serve reset` removes that computer's Serve configuration when you no longer need it. Access through localhost is intended for ordinary `npm start`; private mode uses its printed HTTPS address because account cookies are Secure. No router port forwarding or public website deployment is needed.

Verification: `npm test` covers Google identity separation/linking, existing-account migration, one-use challenges and session rotation, token signature/audience/issuer/expiry/nonce validation, profile isolation, and the existing AI privacy boundary. Tests use generated test signing keys and mocked Google identities; live Google sign-in requires your client ID and approved origin.


## F6: personal preparedness checklist

On Plan ahead, complete the four-step survey and save it. The checklist then replaces the survey. Returning with a saved profile opens the checklist directly; **Edit household answers** returns to the survey. An account is optional. Saving a profile tailors the tasks to explicitly selected care, accessibility, transport, medical-equipment power, and animal needs. Optional/unspecified answers do not trigger assumptions. The curated tasks link to federal Ready.gov guidance reviewed September 26, 2026; they do not report current alerts, evacuation routes, shelter openings or eligibility.

Check a task to record completion. With a saved profile, progress is encrypted in that same SQLite record and belongs to the same browser/account as the profile. Without a saved profile it stays on the page; saving a profile also saves the applicable progress. Returning via the same browser or account restores completion. Editing household answers keeps applicable progress and removes completion for tasks that no longer apply. Deleting the profile deletes its checklist progress. Google-linked and password sign-in share the same record. Checklist progress and household support fields never enter AI requests.

**Print / save as PDF** opens the browser print dialog with only the checklist, progress and source links; the profile form and account controls are excluded. **Download checklist (.txt)** creates a local text file with the same tasks and source URLs. A copyable text panel is also available if an embedded browser blocks downloads. Exports do not include the username, home locality, household size or raw household answers, but task wording can reveal household needs. Keep copies private. Printing/downloading do not send data to another service.

`PUT /api/checklist` accepts `{ taskId, completed }` for an applicable task, with the existing same-origin/profile header and owner checks. It updates only completion against the latest saved answers, so a task change cannot overwrite profile edits. Normal profile saves preserve existing progress. Older encrypted records load with empty progress; no key rotation or database schema migration is required.


## F7: OpenFEMA declaration context

After the Find help now questionnaire, use **FEMA declaration context** beside the official referrals. Filter and select the Virginia locality **where damage occurred**, then choose **Check FEMA records**. Home and current localities are not automatically used. This optional lookup works without a profile, Google configuration or Azure AI. Choosing another locality, going back, restarting or changing accounts cancels the previous lookup and clears its results.

The server sends only Virginia's state code and the explicitly selected county-equivalent code to the fixed OpenFEMA DisasterDeclarationsSummaries v2 endpoint. `virginia-fips.cjs` matches all 133 supported localities against the official Census reference at https://www2.census.gov/geo/docs/reference/codes/files/st51_va_cou.txt (verified September 26, 2026). Cities and counties with the same name have separate codes. No household profile, chat, account identity or precise address is sent to FEMA; declaration results are not sent to AI.

Results show up to ten most recent declaration records for that area, **across all incident types**, with disaster-page links, declared/incident dates, the dataset's Individual Assistance designation, and record update dates. They are historical context and may describe a different event. A declaration or designation does not establish individual eligibility, current applications, deadlines, evacuation instructions or shelter availability. Empty results do not rule out other assistance. Residents should match incident details and confirm next steps with the official resources.

Each successful response shows its last successful check time. Public results are cached in memory by locality for 15 minutes; concurrent requests share one fetch. After cache expiry the server attempts a refresh. Timeout, network failure, malformed data or wrong-area rows yield **declaration status unknown**. If an expired cached result exists, its records remain historical context with their original successful check time and a stale label. An open page also marks results stale after 15 minutes; the resident can check again. Record `lastRefresh` means the record's update time, separate from the successful retrieval time.

`POST /api/declarations` accepts `{ danger: "no", damageLocality }`, requires the same-origin check, JSON content type and `X-HERO-Declarations: 1`, and allows 20 checks per address per minute. Invalid/free-text localities, current-only locality inputs and danger/unsure answers trigger no FEMA lookup. The service has an eight-second upstream timeout and follows no redirects. The browser cancels stale requests when the selection or flow changes. Upstream failures preserve the existing assistance links and chatbot.

`npm test` covers code-map completeness, duplicate county/city names, record validation, empty results, timeouts/failures, cache expiry and recovery, shared requests, exact damage locality, and emergency/origin/privacy boundaries. A live public-area lookup and the browser filter/result flow were also verified during implementation.


## F8: language, accessibility and limited connectivity

Use **Language / Idioma** on any page to choose English or Spanish. The selection persists on this browser when localStorage is available. `language.cjs` contains fixed Spanish interface copy for the public questionnaire, referrals, profile questions, account controls and preparedness tasks. Checklist print/PDF and text exports use the selected language and retain source URLs and task IDs. Input values, stored choices, usernames, locality names, chat messages and original FEMA records are not translated or rewritten. Unknown service error wording falls back to English. No translation service receives personal data. Chat replies and FEMA record details retain their original language; linked official sites have their own language controls. Copy was checked for the emergency/privacy/eligibility boundaries during implementation; professional Spanish-language review and real screen-reader acceptance testing are still release checks, not a claimed certification.

On localhost or HTTPS in a browser with service-worker support, the first connected visit installs a versioned cache of public HTML, CSS, scripts and bundled language/locality content. Later visits can use this public guide when a request fails or takes over 3.5 seconds. Account navigation falls back to a bilingual connection page. APIs, account pages, passwords, saved profiles, household answers, chat, FEMA responses and third-party pages are never added to this cache. The ordinary HTML files contain no personal answers. The offline cache contains no FEMA results or personal data; account/profile saves, Google, chat, FEMA and linked sites need a connection. Failed requests are not queued or sent automatically later. Clear the browser’s site data to remove public caches and preferences; this does not delete server-side SQLite profiles.

A connection notice distinguishes the cached public guide from features needing a connection. Existing drafts remain on the page after a failed save. Chat has a 40-second timeout (including Azure CLI authentication) with an explicit retry button. Its emergency guard rejects any conversation unless the danger answer is “no”. The emergency-screen Continue returns to the safety question; the results-screen Continue focuses the chatbot without clearing answers. Updates to cached source files are versioned by the worker cache name; a new worker installs in the background and takes over after older tabs close. No offline support is claimed for `file://`, private modes that disallow storage, or browsers without service workers.

Completed Find help now answers are retained in the current tab's session storage and included in every chat request. Refreshing or returning from Plan ahead restores the completed questionnaire for the same guest/account; Continue can start a new chat using those answers. Chat history is not persisted. Editing questionnaire answers or changing accounts clears the previous saved help context. Home, current and damage locality controls all use the shared keyboard-accessible dropdown: click to open the list, type to filter, and select an official locality.

Accessibility work includes a focusable skip-link target, visible heading focus after each step, active-panel naming, associated invalid-state/error messages, keyboard-operated locality choices, keyboard-scrollable record/chat areas, reduced motion, forced-color focus, mobile reflow and explicit busy/status announcements. The existing Yes/No/Prefer-not-to-say fieldsets remain intact. No audio or speech feature is included in F8.

Verification: `npm test` covers bundled Spanish safety/question/task coverage, canonical value and URL preservation, translated exports, public-only cache/fallback boundaries, compressed responses/revalidation, emergency navigation and all prior privacy/account/FEMA behavior. Browser checks cover Spanish/English switching, keyboard locality selection, optional profile save-to-checklist flow, persisted settings and guide loading with the preview server stopped.


## F9: conversational AI assistant

After the three Find help now answers, HERO starts a conversation with the configured Foundry agent or direct Azure chat deployment. The assistant gets a fresh authoritative questionnaire summary on every turn, a bounded recent conversation and selected English/Spanish instructions. It suggests an official next step and asks at most one useful question at a time. Canonical locality values and three household location concepts remain distinct. Starting over clears the previous conversation; **Clear conversation** cancels a pending reply and lets the resident start again. Retry resends the failed turn without adding a duplicate bubble. Completed questionnaire answers may be restored from this tab’s sessionStorage after a refresh, while chat messages remain in page memory only, with at most twelve messages and ten thousand characters sent per request. User messages are limited to one thousand characters; provider replies are bounded to 120 words and six thousand raw JSON characters. No server-side conversations, response IDs or chat database are created.

Foundry keeps safety instructions and tools in its stored agent definition; per-request instruction/tool overrides are not supported. The configured prompt agent version 6 retains its model, uses the policy in `chat-policy.mjs`, and has no external tools. Each request sends the validated language preference in its questionnaire summary with `store: false`; direct model requests include system instructions and also opt out of response storage. Saved health/access/support data and checklist progress never enter either provider’s payload. Optional profile context remains explicitly limited to home locality and household size, from the current server-side profile owner. Client-supplied extra message properties, profile IDs and fields are dropped. Azure service monitoring/retention and any agent-level configuration remain governed by that Azure resource; these request settings are not a promise about all provider logs. When replacing or updating the Foundry agent, keep the safety instructions synchronized with `chat-policy.mjs` and leave memory/tool integrations disabled. [Microsoft’s runtime documentation](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/runtime-components) describes stateless Responses calls with storage disabled.

Provider output must be JSON with exactly `reply` and `actionIds`. Replies are rendered as text; action titles and links come from HERO’s catalog. Malformed JSON, unknown/duplicate action IDs, more than three IDs, URLs or HTML in reply text, common address solicitations, empty or excessive output are rejected. The deterministic plan remains usable. Model-supplied HTML is never executed. Prompt instructions prohibit eligibility decisions, current availability claims, evacuation instructions, requests for sensitive identifiers or purported actions on the resident’s behalf; prompt rules and URL checks do not guarantee factual model behavior. Representative access is always available through the official cards.

The original immediate-danger questionnaire gate still prevents AI calls. A narrow additional local guard handles clear urgent English/Spanish chat statements (for example, an explicit statement that the resident cannot breathe) with a 911 referral and emergency action. Ordinary chat pauses until the resident restarts and answers the danger question again. It is not medical triage or a comprehensive emergency detector; the emergency banner remains present. The guard does not authenticate or send that statement to the AI service. Chat request results from a cleared/restarted conversation cannot enter a newer conversation. Same-origin checks support HERO’s configured private HTTPS origin, rate limits stay in place and HTTP redirects are not followed with provider credentials.

### Activate and verify your configured agent

The current local setup is authenticated with Azure CLI. Real English and Spanish replies were verified with synthetic questions and no saved profile. To check it again on this computer:

1. If the CLI session has expired, run `az login` and complete Microsoft sign-in yourself.
2. In the HERO directory, run `npm run check:ai`. This makes two small AI requests, one in English and one in Spanish, with fictional setup questions and no saved household profile. The check prints the reply on success, or a safe failure code and next step; it never prints an endpoint, token or API key.
3. If access is denied, verify the signed-in account’s Foundry Agent Consumer permissions and the endpoint/deployment. The existing direct Azure model option remains supported; no new Azure resource is provisioned by this work.
4. Visit Find help now, finish the questionnaire, and verify that a real reply addresses the selected need and offers an appropriate question or official referral. Retry after signing in works without restarting HERO; restart only after editing `.env`.

`GET /api/chat/status` exposes only whether a valid provider is configured and its kind. It does not claim successful authentication or model readiness. Configuration is distinct from a successful live reply. ## Recovery plans and reviewed helper summaries

`recovery.cjs` is the shared bilingual catalog and text exporter. The browser renders a plan before requesting AI. Its stable action IDs, purposes, approved sources and review dates are also supplied by the server to the provider. Recovery completion lives in owner-aware sessionStorage for this tab, independently of SQLite preparedness progress. It resets for a different need, restarted intake or owner. No database migration is required.

`POST /api/chat` accepts optional `completedActionIds`; invalid IDs return 400. Ordinary success retains `reply` and adds `actionIds` and `mode: "ai"`. Invalid provider output returns 502 with `code: "invalid_output"`. Existing emergency and error contracts remain. Only valid current-plan IDs enter the provider context. Client candidate actions and helper-summary fields are ignored. The browser reports Not checked, Connecting, AI reply received, or AI unavailable from actual request outcomes.

The helper review is constructed locally from selected need/current locality, explicitly selected damage locality, completed/remaining actions, source URLs, editable questions, language and date. Home locality and household size require separate review-screen selection; saved health/access/support answers and chat are never imported. Preview edits are plain text and remain in page memory. Changing optional field selections after manual edits requires rebuilding before export. If plan context changes, a visible notice requests review; it does not silently replace edits. Printing and downloading export the exact preview. The copy fallback remains available if an embedded browser blocks the native flow. Exporting contacts nobody and creates no case record.

Run `npm run sync:ai-policy` to compare the stored agent with local instructions. `-- --apply` creates a new version, preserving the existing model and settings and requiring an agent without external tools. Earlier versions remain available. Version 6 retains the locality-only privacy boundary and covers disasters generally without assuming a particular hazard. Live output can still be rejected; validation is deliberately fail-closed.
